# Экономия лимитов: главный = прораб

Лимит тратят две вещи: **размер контекста главной модели** (перечитывается на каждом шаге) и **цена модели**. Исполнитель/сабагент экономит, потому что работает в чистом контексте на более дешёвой модели и возвращает только итог. Сам по себе он не бесплатный: расходует тот же лимит плана.

## 1. Что кому отдавать
| Задача | Кто | Почему |
|---|---|---|
| Найти, где что лежит; «что вызывает X» | `Explore` (Haiku) | читает много, нужны только `путь:строка` |
| Долгая или шумная команда: установка, тесты, сборка, линтер, миграции, e2e | `runner` (Haiku) | логи не попадают в главный контекст |
| Ревью диффа или листа скриншотов по чек-листу | `reviewer` (Sonnet) | много чтения, нужен вердикт и дефекты |
| Одна фича/модуль с ясной приёмкой | `feature-builder` или сессия на Sonnet | много итераций в чужом контексте |
| Вся производственная работа этапа (спека, фичи, интеграция, QA, релиз) | отдельные облачные сессии на Sonnet | правило пользователя: главный только проверяет и отчитывается (`director` §0) |
| Правка в одну строку по итогам приёмки; всё, что требует знания переписки | главный сам | исполнитель стартует с нуля, на мелочи только дороже |
| Решения, приёмка, ответы пользователю | главный сам | это его работа |
Правило большого пальца: делегировать, если задача прочитает или напечатает больше ~15 тыс. токенов, которые главному потом не нужны.

## 2. Три ошибки
1. **«Сделай как мы обсуждали».** Исполнитель НЕ видит переписку: только свой промпт, задачу, CLAUDE.md и git. Всё важное — в задаче или в файле, на который она ссылается.
2. **`description` — условие срабатывания**, а не описание. Писать: что делает, что отдаёт, чего не делает; для автовызова добавить «use proactively».
3. **Отчёт ложится в контекст главного.** Требовать: «отчёт не больше N строк», результаты — в файлы, в отчёте пути и цифры.

## 3. Шаблон брифа (полный — `docs/briefs/TEMPLATE.md`)
```
Цель: <один результат одним предложением>
Где: <корень, папка; команды запускать из ...>
Можно менять: <файлы/каталоги>. Нельзя трогать: <файлы; кто ещё работает параллельно>
Вход: <пути к спеке/документам, которые надо прочитать; ничего лишнего>
Готово, когда: <проверяемое: npm test, npm run typecheck, npm run build зелёные; новые тесты; скриншоты UI>
Бюджет: <сколько кругов «правка → проверка»>
Не делать: правки вне списка, вопросы пользователю
Отчёт: до N строк — ветка, коммит, цифры, что слабо
```
Общие правила (стиль кода, структура, соглашения) держать в одном файле (`docs/briefs/_common.md`) и давать ссылку, а не пересказывать.

## 4. Поля файла агента (`.claude/agents/<имя>.md`)
Обязательны `name` и `description`. Для экономии:
| Поле | Значение | Когда |
|---|---|---|
| `model` | `haiku` / `sonnet` / `opus` / `inherit` | всегда: самая дешёвая, что справится |
| `tools` | список | только нужные; поиску хватит `Read, Grep, Glob` |
| `maxTurns` | число | потолок расхода на задачу |
| `omitClaudeMd: true` | старт без CLAUDE.md | когда правила проекта агенту не нужны |
| `skills: [имя]` | скилл в контексте со старта | агент всегда работает по одному скиллу |
| `memory: project` | память в `.claude/agent-memory/<имя>/` | агент каждый раз изучает одно и то же |
| `isolation: worktree` | отдельная копия репозитория | параллельные агенты правят одни файлы; не годится, если нужны файлы вне git |
| `effort` | `low`…`max` | `low` для механики |
Агент с именем `Explore` в `.claude/agents/` заменяет встроенный: поиск идёт на Haiku.

## 5. Правила главного
- Не читать большие картинки: один лист ≤ 1500 px, смотреть один раз.
- Не печатать длинные файлы и логи: `grep`, `tail -5`, `cut -c1-200`.
- Не перечитывать то, что в контексте. Между этапами: состояние в `docs/00_STATE.md`, коммит, `/clear`.
- Не больше 2–3 исполнителей сразу: параллельность ускоряет и расход.
- Оборванного по лимиту исполнителя НЕ продолжать через `SendMessage`: возобновлённый может пойти на дорогой модели главного. Запускать нового с явной моделью и брифом «состояние на диске такое-то, продолжай».
- Брифы требуют: «после каждого шага код собирается и тесты запускаются», иначе обрыв оставит сломанное; сломанное вернуть из git.
- Перед возможным обрывом: закоммитить и запушить, обновить STATE. Исполнители коммитят только в свою ветку этапа.
- Перед каждым возвратом исполнителю проверять `used_tokens`; > 200 тыс. → ротация (`director` §4 п. 6).

## 6. Агенты комплекта
- `Explore` — поиск, Haiku, только чтение, ≤ 10 строк `путь:строка`.
- `runner` — тесты, сборка, линтер, установка, миграции, e2e; Haiku; ≤ 8 строк с цифрами; код не правит.
- `reviewer` — ревью диффа и/или листа скриншотов; Sonnet; вердикт + дефекты `файл:строка`; ничего не правит.
- `feature-builder` — одна фича/модуль по брифу; Sonnet; код + тесты + проверки + самопроверка.
Новые файлы агентов подхватываются при старте сессии; если тип не виден — `general-purpose` с `model: sonnet|haiku` и тем же брифом.

## Журнал
Формат: `дата: что случилось → правило`.
- Главный делал всё сам → правило §0 `director`: он только бриф, приёмка, отчёт.
- Исполнитель вырос до ~400 тыс. токенов и упёрся в лимит → ротация при 200 тыс.
- Сабагенту пересказали бриф вместо пути к файлу → детали потерялись; давать путь.
- Опрос фоновой работы каждые пару минут тратил контекст → ждать сообщения.
- Три параллельных исполнителя выбили лимит окна → не больше 2–3, самые ценные первыми.
