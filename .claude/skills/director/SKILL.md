# Главный чат = тех-директор (тонкий контекст, то же качество)

Почему: контекст перечитывается на каждом шаге и съедает лимит. Качество держат **файлы** (требования, решения, брифы, критерии приёмки, цифры): их перечитать — 2–5 тыс. токенов. Дополняет `limits`.

## 0. Правило пользователя — главнее всего ниже
«Этот чат должен только проверять и давать отчёт. Всё остальное — по другим чатам, на моделях, которые ты выбираешь сам: дешевле, но так же качественно.»
Главный САМ НЕ делает: поиск, код и тесты, миграции, установку зависимостей, прогон тестов/сборки/линтера, правки конфигов, ревью диффа. Всё это — брифом исполнителю в ОТДЕЛЬНОЙ облачной сессии (§4: `create_session`, `model: "sonnet"`, бриф и вход в git, отчёт через `send_message`). Сабагенты `Agent` внутри главного для этапов не использовать: его контекст всё равно забивается.
Каждый отчёт главный оценивает 1–10 по «Готово, когда» брифа и цифрам; ниже **9** — возвращает ТОЙ ЖЕ сессии (`send_message`) список конкретных правок с `файл:строка`; принято — merge ветки этапа, STATE, бриф следующей сессии.
Главный делает только: (1) `docs/00_STATE.md` со словами пользователя; (2) бриф этапа с «Готово, когда»; (3) приёмку по одной таблице проверок и одному листу скриншотов; (4) отчёт пользователю; (5) git commit/push принятого.
Самопроверка: если вызов не git, не чтение STATE и не разговор с пользователем — это работа исполнителя.

## 1. Память проекта — файл, а не чат
`docs/00_STATE.md`, ≤ 80 строк, обновлять после КАЖДОГО этапа и перед долгим ожиданием (шаблон — `docs/00_STATE.template.md`):
```
# <проект> — состояние (дата, время)
Цель: <одна строка>.  Ветка: <branch>.  Последний коммит: <hash>
## Решения пользователя (его словами, с датой) — не менять без него
## Требования и архитектура (5–8 строк)
## Этапы: [x] спека [x] архитектура и план фич … [ ] фичи [ ] интеграция [ ] QA [ ] релиз
## Сейчас работает: <сессия, ветка, бриф, когда запущена, что вернёт>
## Цифры последних проверок (тесты, линтер, типы, сборка)
## Открытые вопросы / что слабо
## Следующий шаг
```
**Новый чат начинает так:** CLAUDE.md → этот скилл → `00_STATE.md` → только нужный для шага файл. Не перечитывать переписку.

## 2. Кто что делает
| Работа | Где | Модель |
|---|---|---|
| Разговор с пользователем, решения, приёмка, отчёт | главный | — |
| Спека, архитектура, план фич | отдельная сессия (§4) | Sonnet |
| Фича (каждая — своя сессия и своя ветка; параллельно ≤ 2, файлы не пересекаются) | отдельная сессия (§4) | Sonnet |
| Интеграция веток, QA-прогон, релиз-сборка | отдельная сессия (§4) | Sonnet |
| Поиск по репозиторию | `Explore` | Haiku |
| Тесты, сборка, линтер, установка, миграции, e2e, замеры | `runner` | Haiku |
| Ревью диффа по брифу, разбор листа скриншотов, список дефектов `файл:строка` | `reviewer` | Sonnet |
| Фича/модуль в рамках одной сессии с несколькими кругами «код → проверки» | `feature-builder` | Sonnet |
Этапы: спека → архитектура и план фич → фичи → интеграция → QA → релиз.

## 3. Диета главного
- Вывод команд: `| tail -3`, `grep`; длиннее ~20 строк или дольше ~1 мин — `runner`. Файлы — `sed -n`, `grep -n`.
- Скриншоты: один лист ≤ 1400 px на этап; детали — `reviewer`.
- Не опрашивать фоновую работу: ждать `send_message`. Сабагенту/сессии — путь к брифу, не пересказ; отчёт ≤ 12 строк, логи — файлами. Сабагентов сразу ≤ 2–3.

## 4. Отдельные облачные сессии (работа вне главного контекста)
Инструменты `mcp__claude-code-remote__*` (ToolSearch «claude-code-remote»).
1. Всё нужное исполнителю — **в git** (бриф, спека, тестовые данные): закоммитить и запушить ДО запуска.
2. `create_session`: `source_url` = репозиторий, `source_revision` = текущая ветка, `outcome_branch` = `<ветка>-<этап>`, `model: "sonnet"` (иначе наследует дорогую модель главного), `title`. Промпт:
   ```
   Ты исполнитель этапа «<этап>» проекта <имя>. Сначала: npm ci (зависимости), затем прочитай CLAUDE.md, .claude/skills/director/SKILL.md §4, docs/00_STATE.md и бриф <путь>. Делай только бриф.
   Готово, когда: <измеримо: npm test, npm run typecheck, npm run build зелёные; новые тесты; скриншоты экранов>. Коммить и пушь в свою ветку после каждого рабочего шага.
   В конце отправь главному (send_message, session_id <id главного из get_session>) отчёт ≤ 12 строк: ветка, коммит, что сделано, цифры проверок, что слабо.
   ```
3. В STATE — «Сейчас работает: сессия <id>, ветка, бриф»; ждать. `/clear` безопасен: STATE + отчёт всё восстановят.
4. Приёмка: `git fetch origin <ветка-этапа>` → `runner` гоняет проверки брифа → главный смотрит таблицу и лист → merge → STATE.
5. Застрял/упал: `get_session` (`status_bucket`), `list_events` с `kinds: ["result"]`; новая сессия с брифом «состояние на диске такое-то, продолжай».
6. **Контекст исполнителя ≤ 200 тыс. токенов.** Перед КАЖДЫМ `send_message` исполнителю (правки, возврат) — `get_session` → `external_metadata.context_usage.used_tokens`. Больше 200 тыс. — не писать туда: бриф-передача в файл (`docs/briefs/<этап>_<n>.md`: ветка и коммит, что принято, что осталось, «Готово, когда»), новая сессия с `source_revision` = ветка этапа и `outcome_branch` = та же ветка; старую — `archive_session`.

## 5. «Готово, когда» и оценка
Типовое (команды — из CLAUDE.md): `npm test` зелёный и есть новые тесты на новую логику; `npm run typecheck` без ошибок и новых предупреждений; `npm run build` проходит; для UI — скриншоты экранов (Playwright) на ширине телефона 390 px и десктопа 1280 px; diff в рамках «можно менять», секретов нет.
Оценка 1–10 по этим пунктам; **порог приёмки 9**: ниже — вернуть той же сессии правки с `файл:строка`, пользователю не сдавать. Сводный лист приёмки = таблица «проверка → команда → результат» + один лист скриншотов. Финальный отчёт пользователю: ветка/PR, цифры проверок, лист скриншотов, что слабо, что решить ему.

## 6. Ритм этапа и качество
1. Главный: решение + бриф (файл) + строка в STATE «Сейчас работает». 2. Исполнитель работает, главный ждёт. 3. Отчёт → `runner` (цифры) + `reviewer` (дефекты) → главный: таблица + лист, принять/вернуть. 4. Коммит, пуш, STATE. 5. На границе этапа предложить `/clear`: «состояние в 00_STATE.md».
Качество не падает, потому что: решения пользователя дословно в STATE и брифах; «Готово, когда» — командами и числами, их гоняет `runner`; главный сам смотрит таблицу и лист, рискованные решения (данные, безопасность, платежи) принимает сам; уроки — в журнал.

## Журнал уроков
Формат: `дата: что случилось → правило`.
- Главный сам писал код, гонял тесты и правил конфиги, контекст раздулся → §0: всё, кроме решений, приёмки и отчёта, — исполнителям.
- Исполнитель дорос до ~400 тыс. токенов и упёрся в лимит плана → §4 п. 6: ротация при > 200 тыс.
- Сабагенту пересказывали бриф в промпте, детали терялись → давать путь к файлу брифа.
- Главный опрашивал исполнителя «как дела?» → ждать `send_message`, не опрашивать.
